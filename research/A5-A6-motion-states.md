# A5 Motion and animation · A6 States and micro-interactions

Research for two foundation categories in `research/categories.md`. Researched 2026-10-17 for a desktop web app on
React/Next + Tailwind (no shadcn). **Verified** means checked today with `npm view`, `curl`, the package source or
MDN browser-compat-data 8.1.6 (2026-10-15). Anything marked *(unverified)* is from memory or secondary sources and
needs checking before it goes into a guide. Not a benchmark: a separate animation-library benchmark is in progress,
and its numbers should replace any size or performance claims here.

---

## A5 Motion and animation

### 1. Best topics: questions the guide must answer
1. **What are our duration and easing tokens?** Which token goes on which kind of change (hover, popover, modal, page), and should exits be shorter than entrances?
2. **Spring or bezier curve?** Which one, when, and with what parameters, given that Motion, M3 and SwiftUI each describe springs differently.
3. **Can it be interrupted?** What happens when the user reverses mid-animation (CSS transition vs keyframes vs spring vs View Transition).
4. **Enter/exit and layout changes.** `@starting-style` + `allow-discrete` vs `AnimatePresence`, and FLIP/`layout` vs View Transitions for shared elements.
5. **View Transitions in Next.** Same-document vs cross-document support, and React `<ViewTransition>` status.
6. **Scroll-driven animation in an app.** Where it belongs (progress bars, condensing headers) and the fallback while Firefox lacks it.
7. **What can we animate cheaply?** Compositor-only properties, `transition: all`, and animating height.
8. **Reduced motion done properly.** Reduce motion rather than remove it, and know which libraries ignore the setting by default.
9. **When NOT to animate.** Frequency of use, keyboard-initiated actions, dense data UIs.

### 2. Recommended defaults
| Topic | Default | Why | When to depart |
|---|---|---|---|
| Duration tokens | `instant 0` · `fast 150ms` (hover, press, colour) · `base 200ms` (dropdown, popover, tooltip) · `slow 300ms` (modal, sheet, large layout move). Exits about 20–30% shorter than entrances (300 in, 200–250 out) | NN/g: most UI motion takes 100–400 ms; simple feedback (toggle, checkbox) takes ~100 ms; 200–300 ms for modals; "at 500ms, animations start to feel like a real drag"; exits faster than entrances ([NN/g](https://www.nngroup.com/articles/animation-duration/)). Emil Kowalski: "UI animations should generally stay under 300ms" ([you-dont-need-animations](https://emilkowal.ski/ui/you-dont-need-animations)). M3 grid: short1–4 = 50/100/150/200, medium1–4 = 250/300/350/400, long1–4 = 450–600, extra-long = 700–1000 ms (verified in `@material/web@2.5.0` `_md-sys-motion.scss`) | Marketing and storytelling (F2) can run 400–1000 ms. Large travel across a wide desktop screen can take 350–400 ms. Note that Sonner's own toast transitions are 400 ms |
| Easing tokens | Enter / on-screen move: `cubic-bezier(0.2, 0, 0, 1)` (M3 *standard*). Emphasised enter: `cubic-bezier(0.05, 0.7, 0.1, 1)`. Exit: `cubic-bezier(0.3, 0, 0.8, 0.15)` (M3 *emphasized-accelerate*). Hover/colour: plain `ease` | Ease-out "starts fast and slows down at the end, which gives the impression of a quick response" ([Emil, great-animations](https://emilkowal.ski/ui/great-animations)). The M3 values were verified from the token source. Motion's own default tween is `[0.25, 0.1, 0.35, 1]` over 0.3 s (verified in `motion-dom@14.3.0`) | Use `linear` for progress, spinners and anything scrubbed by scroll. Avoid `ease-in` on entrances because it feels laggy |
| Springs vs bezier | Use a **bezier** for opacity, colour and anything fire-and-forget. Use a **spring** for anything that is gesture-driven, dragged, retargeted or layout-moving. UI spring: `{type:"spring", visualDuration:0.25–0.3, bounce:0}` in Motion, or the M3 *default spatial* spring: stiffness 700, damping ratio 0.9, which in Motion's units is `stiffness:700, damping:47.6, mass:1` (settles in ~170 ms) | Springs carry velocity into a new target, which makes them naturally interruptible ([Josh Comeau](https://www.joshwcomeau.com/animation/a-friendly-introduction-to-spring-physics/), [Motion transitions](https://motion.dev/docs/react-transitions)). M3 spring tokens (verified): spatial fast/default/slow = stiffness 1400/700/300 at ratio 0.9; effects = 3800/1600/800 at ratio 1 (no overshoot on opacity/colour). **Gotcha:** M3 "damping" is a *ratio*, Motion's `damping` is a *coefficient* (c = ratio·2√(k·m)); fast = 67.3, slow = 31.2. Motion's defaults (verified): `x`/`y` default spring 500/25; scale 550/30; `bounce` default 0.3 when you set `duration` | Use `bounce` 0.15–0.3 only for playful moments or a thrown gesture's release. Apple's SwiftUI presets (`.smooth`, `.snappy`, `.bouncy`) use duration + bounce ([WWDC23 "Animate with springs"](https://developer.apple.com/videos/play/wwdc2023/10158/)); the exact bounce values 0 / 0.15 / 0.3 are *(unverified)*. For CSS-only springs, use `linear()` ([generator](https://linear-easing-generator.netlify.app/), [Chrome docs](https://developer.chrome.com/docs/css-ui/css-linear-easing-function)); these are not velocity-preserving |
| Interruptibility | Every state animation must be reversible mid-flight: CSS **transitions** (which retarget from the current value), or Motion/springs. Never use `@keyframes` for toggled state | "Great animations are interruptible… a CSS transition can be interrupted and smoothly transition to a new value" ([Emil](https://emilkowal.ski/ui/great-animations)). Vercel: "Animations are cancelable by user input" ([guidelines](https://vercel.com/design/guidelines)) | Use keyframes for one-shot loops (spinner, shimmer, attention ping) |
| Enter/exit (presence) | Popovers, dialogs and menus use CSS `@starting-style` + `transition-behavior: allow-discrete` on `display`/`overlay`. Use Motion `AnimatePresence` only when exit needs JS orchestration (lists, stagger, route-level) | Zero JS. Baseline: `@starting-style` Chrome 117 / Firefox 129 / Safari 17.5; `transition-behavior` Chrome 117 / Firefox 129 / Safari 17.4 (BCD, verified) ([MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/@starting-style)) | `interpolate-size: allow-keywords` (animating to `height:auto`) is **Chrome-only** (129; Firefox and Safari: no). Use Motion `layout` or `grid-template-rows: 0fr→1fr` instead |
| Shared element / layout | In Next 16 + React 19.3: `<ViewTransition name=…>` for route-level and shared-element changes. Motion `layout` / `layoutId` for in-page reorder, resize and tab underlines | **React 19.3 (2026-09-09) made `<ViewTransition>` and `addTransitionType` stable** ([react.dev blog](https://react.dev/blog/2026/09/09/react-19-3)). Verified: `react@19.3.1` exports `ViewTransition`. Next 16.4.2's bundled guide says "View transitions work in the App Router with no configuration", and `<Link transitionTypes={['nav-forward']}>` tags direction. The old `experimental.viewTransition` docs page now 404s | Inside drag gestures or interruptible layout use Motion `layout`: a View Transition can't be retargeted (a new one skips the running one), and the page is a snapshot while it runs. Keep VTs ≤ 300 ms |
| View Transitions support | Same-document VTs are safe (Baseline Newly available Oct 2025: Chrome 111, Safari 18, Firefox 144). **Cross-document** (`@view-transition { navigation: auto }`) is progressive enhancement only | BCD 8.1.6: `@view-transition` = Chrome 126, Safari 18.2, **Firefox: not supported**. `view-transition-class` / types need Chromium 125+. Next guide: "Without browser support, your application works normally; the transitions do not animate" ([web.dev](https://web.dev/blog/same-document-view-transitions-are-now-baseline-newly-available), [Chrome VT docs](https://developer.chrome.com/docs/web-platform/view-transitions)) | Multi-page sites (docs, marketing) can use cross-doc VTs with no JS |
| Scroll-driven animation | In apps, only for scroll progress, condensing/shadowed sticky headers and reveal-on-enter, all inside `@supports (animation-timeline: view())`. Never hijack scroll | Runs off the main thread with no JS ([Chrome docs](https://developer.chrome.com/docs/css-ui/scroll-driven-animations)). BCD: Chrome 115, **Safari 26**, Firefox "preview" (flag), so it is not Baseline | Story pages (F2) can use GSAP ScrollTrigger where cross-browser parity matters |
| Compositor-only | Animate `transform` and `opacity` only; list properties explicitly; never `transition: all` | Vercel: "Prioritize GPU-accelerated properties (transform, opacity) & avoid… width, height, top, left"; "Never `transition: all`"; "Preference: CSS > Web Animations API > JavaScript libraries" ([guidelines](https://vercel.com/design/guidelines), [web.dev](https://web.dev/articles/stick-to-compositor-only-properties-and-manage-layer-count)) | `filter`/`clip-path` are acceptable on small elements. For size changes, use FLIP (Motion `layout`) to turn them into transforms. Animate a wrapper, not text, to avoid text-smoothing shifts (Vercel) |
| Reduced motion | **Reduce, don't remove:** under `prefers-reduced-motion: reduce`, swap translate/scale/zoom for opacity crossfades ≤ 200 ms, keep state feedback, and stop parallax, autoplay and scroll-linked motion. In Motion, set `<MotionConfig reducedMotion="user">` at the root | Apple HIG: "Replacing transitions in x-, y-, and z-axes with fades", "Tightening animation springs to reduce bounce" ([HIG Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). **Motion's default is `reducedMotion: "never"` (verified in `framer-motion@14.3.0`), so it ignores the OS setting unless configured.** `"user"` drops transforms and layout but keeps opacity ([Motion a11y](https://motion.dev/docs/react-accessibility)). WCAG [2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) (AAA) and [2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html) (A: pause controls for motion over 5 s). Tailwind: `motion-safe:` / `motion-reduce:` | Essential motion (progress, a drag following the finger) stays. Sonner and Next's VT guide example remove *all* motion under reduce. The Next guide itself calls preserving crossfades "a more refined approach" |
| When NOT to animate | No animation for keyboard-initiated actions, the command palette (⌘K), anything used hundreds of times a day, per-keystroke filtering, table sorts, or tooltips after the first (show these instantly) | Emil: "never animate keyboard initiated actions"; Raycast has "no animation at all. That's the optimal experience". Once a tooltip is open, others open "with no delay and no animation". Apple HIG: "generally avoid adding motion to UI interactions that occur frequently" ([HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)). Vercel: "Only animate when it clarifies cause & effect" | First-run, empty-state, success-of-rare-action and onboarding moments can afford delight |

### 5. Disagreements with the A5 row in `research/categories.md`
- **Tools column omits the native stack, which should be our default.** CSS transitions + `@starting-style`, plus React 19.3's stable `<ViewTransition>`, cover most app motion with zero JS. Motion is for springs, layout, gestures and presence orchestration. "View Transitions API" is listed but without noting the React/Next integration is now stable and config-free.
- **Rive and Lottie are not UI motion tools.** They are illustration/asset runtimes with paid authoring; move them to A10 (Icons and imagery) or F.
- **GSAP needs a licence flag in the row.** It is free, but not OSI, with a Webflow field-of-use restriction. It fits F2 (scroll storytelling) better than app UI.
- **Add candidates:** AutoAnimate (zero-config lists) and anime.js v4 (MIT, small). React Spring is maintained (v10, v11 beta) but second to Motion.
- **References:** Family is an iOS app with no web surface, so use benji.org/family-values videos or drop it. Linear's motion is mostly in-app (login). Add Emil Kowalski, Chrome VT demos, scroll-driven-animations.style and the Next VT demo, which are all capturable.
- **Covers column should add:** duration/easing **tokens** (these overlap A1, so define them alongside colour tokens), and **"when not to animate"**, the single most useful rule for a desktop productivity app. Keep "scroll-driven" limited to progress/headers here and leave storytelling to F2.

## A6 States and micro-interactions

### 1. Best topics: questions the guide must answer
1. **What is the full state matrix for every interactive element?** default, hover, active/pressed, focus-visible, selected, disabled vs aria-disabled, loading, success, error, read-only.
2. **What feedback does each latency band get?** <100 ms, 100 ms–1 s, 1–10 s, >10 s.
3. **Skeleton, spinner or progress bar, and with what show-delay and minimum-visible time?**
4. **What does a button do while its action is in flight?**
5. **When is optimistic UI safe, and how does rollback look?** `useOptimistic` vs TanStack Query.
6. **Undo or confirm?** And how long does the undo window last?
7. **Toasts:** placement, stacking, duration, actions, a11y, and what must *not* be a toast.
8. **Changing numbers:** how should counters, prices and KPIs animate, and when shouldn't they?
9. **Hover intent:** tooltip delays and menu safe areas (submenu triangles).

### 2. Recommended defaults
| Topic | Default | Why | When to depart |
|---|---|---|---|
| State matrix | Every control ships all states. Hover is gated to `(hover:hover)` (Tailwind v4 `hover:` already does this, verified in [upgrade guide](https://tailwindcss.com/docs/upgrade-guide)). Hover/active/focus *raise* contrast. Active = darker fill or `scale(0.97–0.98)` at 100–150 ms. `:focus-visible` ring 2 px + 2 px offset, never removed | Vercel: ":hover, :active, :focus have more contrast than rest state" ([guidelines](https://vercel.com/design/guidelines)). WCAG 2.4.7 focus visible (AA) | The `scale(0.97)` press value is a common Emil Kowalski / Linear convention *(unverified as a published number)* |
| Disabled | Disable only when the action is impossible right now, and explain why (tooltip or helper text). Otherwise keep the control enabled and validate on submit | Geist Button: "Disable a button only when the action is impossible right now (missing input, insufficient permission)" ([vercel.com/geist/button](https://vercel.com/geist/button)). Vercel: "Allow submitting incomplete forms to surface validation feedback" | Use `aria-disabled="true"` (still focusable) when a reason must be discoverable by keyboard/screen reader |
| Latency bands | <100 ms: no indicator (feels direct). 100 ms–1 s: no spinner; optional subtle pressed/pending state. 1–10 s: indicator. >10 s: determinate progress + Cancel. Mutations target <500 ms | NN/g 0.1 / 1 / 10 s limits; ">10 seconds needs a percent-done indicator as well as a clearly signposted way for the user to interrupt" ([NN/g](https://www.nngroup.com/articles/response-times-3-important-limits/)). Vercel: "POST/PATCH/DELETE complete in <500ms" | Streaming AI output (E1) shows tokens instead of a spinner |
| Spinner/skeleton timing | **Show-delay 150–300 ms; minimum visible 300–500 ms** (no flash on fast responses) | Verbatim Vercel guideline; "The `<Suspense>` component in React does this automatically" ([guidelines](https://vercel.com/design/guidelines)) | Skip the delay for actions known to be slow (export, deploy) and show progress at once |
| Skeleton vs spinner vs progress | **Skeleton** for page or region loads with known layout (it must mirror the final layout exactly, with no CLS). **Inline spinner** for one control or small module. **Determinate bar** for >10 s or file transfers. Nothing under ~1 s | NN/g: spinners and skeletons for 2–10 s; "progress bars are strongly recommended for any page that takes longer than 10 seconds"; looped animation under 1 s "is distracting" ([skeletons](https://www.nngroup.com/articles/skeleton-screens/), [progress](https://www.nngroup.com/articles/progress-indicators/)). Vercel: "Skeletons mirror final content exactly to avoid layout shift" | For unknown layout (search results of variable type), use a spinner over a fake skeleton |
| Button loading | Keep the label and width. Show an inline spinner (left of label or replacing an icon) plus `aria-busy`. Keep the button focusable. Block re-submit while in flight. Send an idempotency key | Vercel: "Show a loading indicator & keep the original label"; "disable during the in-flight request, show a spinner, & include an idempotency key". Geist: "Pass `loading` instead of swapping in a spinner so the button stays focusable and announces the busy state" | Use "Saving…"-style ellipsis text (Vercel) when the action has no icon slot |
| Optimistic UI | Go optimistic when success is very likely and the action is reversible (toggle, rename, reorder, status change). On failure: roll back, show an error toast with Retry, and keep the user's input. Server Actions use React 19 `useOptimistic`; client cache uses TanStack Query (`variables` pattern for simple cases; `onMutate` snapshot → `onError` restore → `onSettled` invalidate for shared cache) | Vercel: "Update the UI immediately when success is likely; reconcile on server response. On failure, show an error & roll back or provide Undo". `useOptimistic` reverts automatically when the transition settles ([react.dev](https://react.dev/reference/react/useOptimistic), [TanStack](https://tanstack.com/query/latest/docs/framework/react/guides/optimistic-updates)) | Never for payments, permissions, irreversible sends, or actions with server-computed results (prices, IDs) |
| Undo vs confirm | **Undo by default** for reversible destructive actions (archive, delete via soft-delete): past-tense toast + single "Undo", **5–10 s window**. **Confirm** only for irreversible or costly actions; type-to-confirm only for catastrophic ones | NN/g: confirmations get habituated ("users automate their response"); "do try your best to offer undo" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). Geist Toast: "Undo snackbars stay on screen for 5–10 seconds and pair the past-tense toast with a single Undo action button" ([vercel.com/geist/toast](https://vercel.com/geist/toast)) | Bulk destructive ops on many items: confirm with count, *and* offer undo |
| Toast behaviour | Bottom-right on desktop, ≤ 3 visible (stacked, expand on hover), 4 s default, pause on hover and when the tab is hidden, `aria-live="polite"`. One toast per async flow (the terminal step), ≤ 6 words, past tense | Sonner defaults verified in `sonner@2.0.8` source: `position='bottom-right'`, `VISIBLE_TOASTS_AMOUNT=3`, `TOAST_LIFETIME=4000`, width 356, gap 14, viewport offset 24px, `aria-live: polite`, pauses on `document.hidden`, Alt+T hotkey to focus the region. Geist: "Don't stack toasts to narrate one async flow" | Action toasts (Undo) get 5–10 s or stay until dismissed (WCAG [2.2.1](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)). Never toast-only for errors the user must triage, field validation, or billing/permission failures: use inline or persistent UI (Geist; [Adrian Roselli](https://adrianroselli.com/2020/01/defining-toast-messages.html)) |
| Number transitions | Animate only user-caused or rare changes (KPI after a filter, price after a plan toggle) with NumberFlow. Always `font-variant-numeric: tabular-nums`. Honour reduced motion | NumberFlow: `Intl.NumberFormat`-driven digit roll; defaults verified as 900 ms transform / 450 ms opacity, `respectMotionPreference: true`. Vercel lists `tabular-nums` for numbers | For high-frequency live data (≥ 1 update/s, C6), don't roll digits: swap with a brief colour flash or none |
| Hover intent | Tooltips: ~400–700 ms initial delay, then instant (no delay, no animation) while moving between triggers. Submenus: safe-triangle or hover-intent area | Emil: after the first tooltip, others open "with no delay and no animation". Linear: draws "a triangle between the mouse cursor and the sub-menu" so a diagonal path doesn't close it ([Linear](https://linear.app/now/invisible-details)) | The exact tooltip delay value is *(unverified)*; Radix defaults to 700 ms *(unverified)* |

### 5. Disagreements with the A6 row in `research/categories.md`
- **References Superhuman and Things can't be captured publicly** (login or paid native apps), and Linear's state polish is in-app. Replace them with Vercel Geist (Button, Toast, Skeleton), Sonner, NumberFlow, Linear's invisible-details post and Rauno's essay. All load without login.
- **Overlap needs a boundary.** A6 should own *timing and state rules* (latency bands, show-delay, undo window, state matrix). B4 owns the toast/drawer *components* and B8 owns page-level empty/error/offline. Otherwise toasts and skeletons are specified three times.
- **Tools:** add **React 19 `useOptimistic`** (the default for Server Actions in Next) and **react-hot-toast** (runner-up). Keep **Vaul** out of A6: it is a drawer (B4) and self-declared unmaintained (last publish 2024-12-14). Note that Motion's `AnimateNumber` is paid (Motion+), which makes NumberFlow the free pick.
- **Covers should add** "disabled vs aria-disabled", button loading, hover intent (tooltip delay, submenu triangles) and latency bands. Those are the decisions agents most often get wrong.
