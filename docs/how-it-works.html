How the UX library works

A shared memory of the best UX on the web, which any Claude session can search while building. You feed it links, screenshots and names; it captures, analyses, scores and files them; agents pull the right reference, the evidence and working code into whatever they're building.

The map

Everything lives in one Git repo. There's no database or server: entries are folders of Markdown, images and code, and a build step turns them into a searchable index and the gallery.

How an agent finds a reference (/ux-find)

Any Claude session with the skill installed calls it when it's designing or building UI, or when you ask directly. It works through the layers from general to specific:

  1. Locate the library. It uses a local clone (sibling folder or ~/ux-design), or clones it, then pulls the latest.
  2. Read the map. guides/README.md explains the layers and how to answer, and lists tools to avoid (unmaintained, licence-restricted or deprecated). For a whole brief ("a trading terminal"), guides/scenarios.md gives a starting stack, what must be right and what to test.
  3. Search with the team's vocabulary. scripts/find.mjs maps the request's words to categories, guides and entries ("snackbar" finds toasts, "frosted" finds materials, "live cursors" finds the collaboration gap), matches whole words only, and prints how well the library covers the request before anything else. Words it misses get added to guides/aliases.json.
  4. Classify the request. A category question ("I need a chart", "should this be 3D?") goes to the category guide and the scored sources. A look question ("a dark hero", "a pricing toggle") goes straight to patterns.
  5. Decide with evidence. The guide picks the form from the job; SOURCES.md and the profiles pick the library by fit, not just score.
  6. Check coverage, then explore if needed. The library is curated recommendations, not a closed list. When it's thin for the request (or something outside it is clearly better), the agent researches the gap itself: web search, licence and maintenance checks, a live capture of the best products, and a rough score against the rubric.
  7. Return references. A coverage line first (strong, partial or none), then one recommendation with its score, a runner-up, the defaults to change, then the top patterns with screenshots (it views them first) and the techniques that apply. Each is labelled Curated (in the library) or Explored (found this session), with an offer to add good finds through /ux-add.
  8. Hand over code. Runnable benchmark code or option.js for libraries; a clean-room example.tsx in our React/Tailwind stack for site patterns, committed back so the next session reuses it.

Example: a chart

Build task: "Add a 6-month daily active users chart to the admin dashboard."

Use Recharts (7.5/10) for this: it's our default for everyday charts in the Next app, it's native JSX, and its keyboard layer gave the best accessibility of the React libraries. For 180 days of data, use an area chart with a range slider (<Brush>).

Change these defaults: pass our validated palette, set the legend order, and label the Brush yourself (its built-in label reads "Min value: undefined").

Runner-up: ECharts (7.8) if you need wheel zoom, drill-down or 10k+ points. Ready code: chart/echarts-datazoom-time-series and bench/libs/recharts.jsx.

read: guides/README.md → guides/charts.md → SOURCES.md → sources/recharts → bench/libs/recharts.jsx

Example: a premium product page

Build task: "Make the product page hero feel premium. Should we use 3D?"

Probably not real-time 3D. The guide's first question is whether 3D shows something 2D can't. For an art-directed hero, pre-rendered media like Apple's AirPods page (★★★★★) looks better and costs less.

If customers need to inspect the product, use model-viewer (7.5): one tag, built-in hotspots and keyboard access. See 3d/modelviewer-hotspot-annotations.

Defaults to keep: a poster first, lazy loading, and stopping motion under reduced motion. Most reference sites skip that last one, so it's a place to beat them.

read: guides/3d.md (step 0) → entries/3d/apple-airpods-scroll-story → sources/model-viewer

How an agent adds a reference (/ux-add)

The skill picks a capture route from what you give it, then files the result the same way every time.

You give itWhat it doesWhat gets saved
A URLLive capture at desktop and phone widths; opens menus or panels when needed (hover, click)desktop.jpg, mobile.jpg, crops, and source.html + styles.json for a focused element
A 3D or motion-heavy URLWaits for heavy scenes, captures scroll frames, checks reduced motionImages plus evidence.json (weight, engine, canvas labels, motion behaviour)
A screenshotSaves and analyses it; asks for the source URLThe image, flagged needs_capture until a live capture replaces it
Just a name ("apache charts")Searches to find the real site firstAs for a URL
An open-source libraryInstalls it, runs the shared benchmark, scores itA source profile, benchmark render and code, plus patterns for anything best-in-class

Then, every time: one entry per pattern (a page can yield several), a rating of 3 to 5 stars (anything weaker isn't kept), duplicate check, npm run catalog, commit to main, and republish the gallery. If the gallery can't be republished, the skill says so instead of skipping it.

How we use it

Feeding it

  • Paste a link or screenshot into any Claude session and say "add this to the UX library", or type /ux-add.
  • Say what caught your eye ("the pricing toggle") so the capture focuses on it.
  • For signed-in screens (dashboards, apps), send a screenshot or recording. Those can't be captured automatically.

Using it

  • While building, just describe the UI; sessions with the skill installed consult it. Or ask: "find a good empty state in the UX library".
  • Browse the published gallery: filter by pattern, tags or rating; switch to the Sources tab for library scorecards.
  • On GitHub, CATALOG.md and SOURCES.md are the tables.

Reviewing

  • Entries land on main straight away. Skim new ones in the gallery and fix tags or ratings in entry.md.
  • Delete what doesn't earn its place. Fewer, better references beat a big pile.

Deciding

  • Use scores to compare, and the guides to choose. A lower-scoring library can be the right fit.
  • When a session departs from a default, it should say why. Push back if the reason is weak.

Setup

In a project repo (local and cloud)

Add the library's plugin to the project's .claude/settings.json:

{
  "extraKnownMarketplaces": {
    "ux-design": { "source": { "source": "github", "repo": "toby1tobytoby3/UX-Design" } }
  },
  "enabledPlugins": { "ux-library@ux-design": true }
}

Locally, once

/plugin marketplace add toby1tobytoby3/UX-Design
/plugin install ux-library@ux-design

Cloud sessions

  • Attach the UX-Design repo to the session or environment so skills can read and push entries.
  • Live capture needs network access to the sites you add. The environment used to build this has open access; a restricted environment can still use screenshots and search.

Guidance, not rules

Guides give defaults as default → why → when to depart. Real projects have edge cases; sessions should depart when the reason doesn't apply, and say so. Only two limits are hard:

  • No invented evidence. Screenshots and numbers are captured or measured, never made up. Anything not live-captured is flagged.
  • No pasting captured third-party code into our codebase. It's reference only. Open-source code under its licence is fine, and that's why library benchmarks ship runnable code.
