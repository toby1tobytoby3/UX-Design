# Choosing 3D

`ux-find` reads this for any 3D or WebGL request. **Step 0** decides whether 3D is justified at all.
**Step 1** picks the form. **Step 2** picks the library from `SOURCES.md` (`3d`) and the profiles in
`sources/` (every library did the same four tasks with the same model; see `bench3d/`). **Step 3** applies the house rules.

## 0. Should this be 3D at all?
3D costs 150–850 KB of JavaScript, megabytes of assets, battery, and accessibility work. Use it only when it
shows something 2D can't:

| Use 3D when… | Don't, use 2D, video or images when… |
|---|---|
| Shape, scale or material is the point (a product people would turn over in their hands) | It's decoration behind text |
| The user configures something visual (colour, parts, size) | A 6-second loop would say the same thing (use a video) |
| Spatial relationships matter (a floor plan, an assembly, a route) | The content must be read, compared or scanned |
| One signature brand moment, done well | Every section "needs to feel premium" |

## 1. Form: what is the 3D doing?
| Job | Form | Notes |
|---|---|---|
| Show one product | **Product viewer**: orbit, soft shadow, hotspots, AR on phones | Poster first; drag hint; no auto-rotate with reduced motion |
| Let users customise | **Configurator**: viewer + swatches that swap materials | Controls are normal HTML buttons, not 3D |
| Hero or brand moment | **Hero scene**: one model or abstract form, subtle pointer parallax | Must not block the headline; static poster on mobile if heavy |
| Tell a story while scrolling | **Scroll-driven scene**: camera or model moves with scroll | Keep the text in HTML; scene is illustration |
| Data in space (globe, network) | **3D data view** | Usually worse than 2D; justify it |
| Decorative motion | **Shader background** | Tiny (OGL); pause off-screen; disable with reduced motion |

## 2. Library: which source fits the job?
Overall scores are in `SOURCES.md`; **fit beats score**. Start from the first row that matches.

| If the job is… | Use | Score | Why (evidence) | Runner-up |
|---|---|---|---|---|
| Show one product in 3D (product page, launch, docs), maybe AR | **model-viewer** | 7.5 | One tag; best out-of-box look; keyboard + alt + button hotspots built in | React Three Fiber |
| Any custom scene in our React/Next app (hero, configurator, scroll story) | **React Three Fiber + drei** | 8.5 | Best look for least code; `<Html>` hotspots, ContactShadows, Instances; React 19 | three.js |
| Custom scene outside React, or tight render-loop control | **three.js** | 7.3 | The engine itself; 160 KB gz tree-shaken | React Three Fiber |
| A 3D application (simulator, twin, XR, editor) | **Babylon.js** | 7.0 | Full engine, keyboard camera by default; 846 KB gz | three.js |
| A tiny shader effect where every KB counts | **OGL** | 5.8 | 25 KB gz; you write the shaders | three.js |

## 3. House rules (apply whichever library you pick)
- **Poster first.** Render a static image (also the SEO and no-WebGL fallback), then lazy-load the 3D with
  `next/dynamic(..., { ssr: false })` when it scrolls into view. Never block first paint on WebGL.
- **Asset budget.** Compress models (glTF with Draco or Meshopt, KTX2 textures; `gltfjsx --transform` for R3F).
  Aim for < 2 MB per scene on mobile. Self-host environment maps; never fetch HDRs from a third-party CDN at runtime.
- **Render only when needed.** On-demand frames (`frameloop="demand"` / redraw on change), cap DPR at 2,
  pause when off-screen, instancing for repeats.
- **Reduced motion.** No auto-rotate, parallax or scroll-scrubbed camera under `prefers-reduced-motion`.
- **Accessibility.** The canvas is invisible to screen readers and, in three.js, R3F and OGL, unreachable by
  keyboard. Give it a text alternative (`role="img"` + label, or `alt` in model-viewer), make controls real
  HTML buttons, and never put essential information only in 3D.
- **Colour.** glTF colours are linear; let the library handle sRGB output (OGL won't). Match the background
  to the page so the canvas doesn't read as a box.
- **Test on a real mid-range phone.** Our benchmark timings come from a software GPU and are only relative.
